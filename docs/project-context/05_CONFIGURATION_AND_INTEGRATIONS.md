### Model YAML variants (`configs/models/`)
- 110 generated YAML files, one per VARIANT
- Each file name: `yolo11<scale>_<name>.yaml` (the scale must be in the filename for `ultralytics` `guess_model_scale()` to work correctly)
- Contents: backbone rows + head rows + optional `sar_loss` block
- Generated by: `python -m saryolo arch --variant <name> --out <dir>` or programmatically via `arch.py`
- Key YAML structure:
  ```yaml
  # SAR-YOLO generated file
  # Regenerate with: python -m saryolo arch --variant full_s
  # scale=s  levels=p3-p4-p5  modules=sfe,sfm,saa,amf,p2_head
  # efficiency_arm=False  (True = the arm exists for the cost claim)
  
  nc: 1
  scale: s
  
  backbone:
  - [-1, 1, "RatioSpaceCFARFrontEnd", ["ch", "cfar"]]  # or "conv"/"fixed" if enabled
  - [-1, 1, "SARInputAdapter", ["ch", "hybrid"]]  # or "identity"/"local"/"learned"
  - [-1, 1, "Conv", [64, 3, 2]]  # P1/2
  - [-1, 1, "Conv", [128, 3, 2]]  # P2/4
  - [-1, 2, "C3k2", [256, False, 0.25]]  # P2 C3k2, repeats 2
  # ... more backbone rows
  - [-1, 2, "C3k2", [512, True]]  # P4 C3k2 with double path
  - [-1, 1, "Conv", [512, 3, 2]]  # P4/16
  - [-1, 2, "C3k2", [1024, True]]  # P5 C3k2 with double path
  - [-1, 2, "C3k2", [1024, True]]  # P5 C3k2, repeats 2
  - [-1, 1, "SPPF", [1024, 5]]
  - [-1, 2, "C2PSA", [1024]]
  # ... per-level slots (prior, attention, context, refinement, SSAC) per detection level
  - Detect [1]  # nc=1
  
  # Optional sar_loss block (if the variant uses the SAR-aware criterion)
  sar_loss:
    w_sep: 0.2
    w_small: 0.5
    w_smooth: 0.05
    margin: 1.0
    bg_frac: 0.25
  ```

### Experiment configs (`configs/exp/EXP-001_baseline.yaml` through `EXP-019_*.yaml` + ablations + frontier)
- Human-readable YAML configs that reference VARIANT names
- Each file specifies: `exp`, `model`, `data`, `train`, `val`, `test` paths; `nc` (number of classes); `epochs`; `batch_size`; `imgsz`; `device`; `optimizer`; `lr0`, `lrf`; `momentum`; `weight_decay`; `warmup_epochs`; `warmup_momentum`; `seed`; and any experiment-specific overrides (e.g., `sar_loss` weights, `ssac` settings, `conditioning` mode, etc.)
- EXP-001 = baseline (stock YOLO11, no SAR modules)
- EXP-002 = + Component 1 (SFE)
- EXP-003 = + Component 2 (SFM)
- EXP-004 = + Component 3 (SAA)
- EXP-005 = + Component 4 (AMF)
- EXP-006 = + P2 head
- EXP-007 = FULL (all modules + P2 head + SAR loss)
- EXP-007 noloss = FULL architecture with SAR loss switched off (ablation control)
- EXP-013..016 = v2 cumulative ladder (clutter, prior, frequency, context additions)
- EXP-017 = v2 full (v1 + clutter + prior + frequency + context + refinement, Components 1-11)
- EXP-018 = v2 without spectral (Module G removal)
- v2_lite_* = efficiency frontier arms (full v2 minus context and AMF)
- ablations: `att_se`, `att_eca`, `fus_concat`, etc.
- ARM variants: `v2_noclutter`, `v2_noprior`, `v2_nofreq`, `v2_noctx`, `v2_norefine`

### Data YAML configs (`configs/datasets/*.yaml`)
- Dataset registration: `train`, `val`, `test` paths (relative to data root); `nc` (number of classes); `names` (class name dict, e.g., `{0: "ship"}`)
- Example (`hrsid_real.yaml`):
  ```yaml
  path: datasets/processed/hrsid_real  # root dataset directory (relative to cwd)
  train: images/train  # train split images dir
  val: images/val  # val split images dir
  test: images/test  # test split images dir (may not exist for some datasets)
  nc: 1
  names: {0: "ship"}
  ```
- Paths are **relative** to the working directory (not absolute, machine-specific)
- `!configs/datasets/generated/` is excluded from git (machine-specific paths)

### Augmentation config (`augmentation/sar.py`)
- `AugmentationPlan(kinds, views, include_clean, severities)`: defines what corruptions to apply, how many views, whether to include the clean original, and the severity values per kind
- `severities` format: `{"speckle": (8, 4)}` = tuple of (parameter1, parameter2) per corruption kind

- **Custom layers**: 12+ SAR-specific modules registered via `saryolo.nn.register`, making them resolvable from any Ultralytics YAML

- **Key APIs used**:

## SAR-Specific Configuration

### Acquisition Metadata Structure
Per-image metadata triple: `(continuous, categorical, availability)`

| Field | Type | Example Values | Description |
|---|---|---|---|
| `continuous` | float | `1.5` | Physically-ordered descriptor: e.g., `resolution_m` (meters), incidence angle, band power |
| `categorical` | int | `0`, `1` | Embedded descriptor: e.g., `sensor` (VV/VH polarization), `mode` (scan mode) |
| `availability` | int | `1` | Binary: is the acquisition known/verified? |

The `MetadataTable` (built by `saryolo metadata` or `write_acquisition_metadata`) maps image stem → `(continuous, categorical, availability)`.

The vocabulary of categorical values is learned from the dataset; e.g., `sensor` might have vocabulary `{0: "VV", 1: "VH"}` and `mode` might have `{0: "scan", 1: "stare"}`.

### Conditioning Modes (for `AcquisitionConditionedAdapter`)
Two dimensions are wired:

1. **Mode**: how the metadata modulates the feature
   - `scale`: scale shift (additive modulation)
   - `shift`: offset modulation
   - `film`: per-channel modulation from sensor and resolution (the proposed arm)
   - `sensor`: sensor embedding only (cannot transfer to unseen sensor by construction)
   - `resolution`: resolution only (continuous field, exists for any sensor)
   - `continuous_only`: physical descriptors only (resolution, band, incidence) — the arm that can reach an unseen sensor
   - `spatial`: position-dependent modulation (most expressive)

2. **Field set**: which acquisition parameters are consumed
   - `all`: all available fields (sensor + resolution + gain + mode)
   - `continuous_only`: only physically-ordered fields (no learned embeddings)
   - `sensor`: sensor embedding only
   - `resolution`: resolution only

The `continuous_only` arm matters most for the headline claim: it uses only fields that a deployment is most likely to know (sensor model publishes resolution, band, incidence; these are not learned embeddings that would need retraining for a new sensor).

### SAR-Aware Loss Configuration
The `sar_loss` block in model YAML (optional):

```yaml
sar_loss:
  w_sep: 0.2      # separation term weight
  w_small: 0.5    # small-target term weight
  w_smooth: 0.05  # smoothness term weight
  margin: 1.0     # margin for separation term
  bg_frac: 0.25   # background fraction for loss computation
```

These values are initial defaults for EXP-007 (FULL); they are tuned by the EXP-008 sweep and recorded here so every run is reproducible from the committed YAML alone.

The SAR-aware criterion is read by `SARYOLODetectionModel.init_criterion()` (model.py) or `RTDETRDetectionModel.init_criterion()` (model.py RT-DETR facade), using the YAML `sar_loss` block rather than the trainer's argument namespace (which rejects unknown keys).

### SSAC Execution Configuration
SSAC execution is configured via CLI arguments or experiment config:

| Argument | Meaning | Default |
|---|---|---|
| `--ssac-execution dense/sparse` | Dense: expensive path everywhere; Sparse: only on selected tiles | `dense` |
| `--ssac-keep FRACTION` | Fraction of tiles to refine (sparse only); at least 1 tile always selected | `0.25` |
| `--ssac-tile SIZE` | Spatial tile size for sparse execution (feature-map pixels) | `16` |
| `--ssac-penalty FLOAT` | Sparsity weight added to loss (`sparsity * mean(gate_means)`) | `0.0` (off except in deliberate sparsity arm) |
| `--ssac-tau FLOAT` | Temperature of allocation sigmoid | `1.0` |
| `--ssac-select FLOAT` | Threshold on gain map for reporting selected fraction | `0.5` (diagnostic, not a switch) |

In experiment YAMLs, SSAC settings are under the `ssac` key of the ModelSpec, e.g.:
```yaml
ssac: adaptive
ssac_scales: [3, 7]
ssac_hidden: 16
ssac_expand: 2
ssac_execution: dense
ssac_tile: 16
ssac_keep: 0.25
ssac_penalty: 0.0
ssac_tau: 1.0
ssac_select: 0.5
```

### CFAR Configuration
CFAR front end mode and scales:

| Parameter | Meaning | Default |
|---|---|---|
| `mode` | `cfar` (proposed), `conv` (matched-cost control), `fixed` (fixed-threshold control) | `cfar` |
| `scales` | Local-statistics window sizes (odd integers >= 3); geometric progression | `(3, 7, 15)` |

In model YAML (row 0 of backbone):
```yaml
backbone:
- [-1, 1, "RatioSpaceCFARFrontEnd", ["ch", "cfar"]]
# or
backbone:
- [-1, 1, "RatioSpaceCFARFrontEnd", ["ch", "conv"]]
# or
backbone:
- [-1, 1, "RatioSpaceCFARFrontEnd", ["ch", "fixed"]]
```

### Input Adapter Mode
SIA mode controls the input representation:

| Mode | Additional params (at c1=3) | Description |
|---|---|---|
| `identity` | 0 | Raw intensity; the control |
| `local` | ~43 | Local-statistics representation (mean, std, high-pass) |
| `learned` | ~98 | Learned representation only, no explicit statistics |
| `hybrid` | ~164 | Proposed: both streams fused by learned 1x1 projection |

In model YAML (first backbone row):
```yaml
backbone:
- [-1, 1, "SARInputAdapter", ["ch", "hybrid"]]
# or "identity", "local", "learned"
```

## Deployment Configuration

### Streamlit Deployment
- **Default weights**: `weights/sarvo_ssac001.pt` (committed checkpoint with provenance and checksum in `weights/README.md`)
- **Weight resolution order** (`resolve_weights()` in `app.py`):
  1. `SARVO_WEIGHTS` environment variable
  2. Documented default: `weights/sarvo_ssac001.pt`
  3. If neither: empty string → app reports "No checkpoint is configured" and disables detection
- **Hosted instance check** (`scripts/verify_deploy.py`):
  ```bash
  python scripts/verify_deploy.py --url https://<app>.streamlit.app
  ```
  - Exits non-zero on failure (e.g., weights not loaded, model error)
  - Used by the project to verify deployed instances

### CLI Weight Resolution
Most CLI commands that accept `--weights`:
- If `--weights` is provided: use that path directly
- If `--weights` is not provided: behavior varies by command
  - `train`: requires `--exp` which references a config that may implicitly reference a checkpoint via `resume` or not
  - `eval`, `predict`, `robustness`, `gain`, `efficiency`: `--weights` is typically required (not optional)
  - `probe`: `--weights` is required; also needs `--metadata` or `--dataset` for acquisition conditioning

### Dataset Configuration for Training
Every training experiment needs a `data.yaml` with:
- `path`: root dataset directory (relative to cwd)
- `train`: images/train dir (relative to `path`)
- `val`: images/val dir (relative to `path`)
- `test`: images/test dir (relative to `path`; may not exist)
- `nc`: number of classes
- `names`: dict mapping class index to name, e.g., `{0: "ship"}`

The HRSID real dataset config (`configs/datasets/hrsid_real.yaml`) provides this for the pilot subset. Other datasets (SSDD, SARDet-100K, etc.) would have their own configs.

## Configuration Consistency

The repository enforces configuration consistency through:

1. **Test assertions**: `test_readme_cost_table_matches_the_measured_models`, `test_variant_filenames_encode_scale`, `test_declared_scale_variants_build` — these check that README numbers match measured models, that variant filenames encode scale correctly, and that declared scale variants build successfully.

2. **Variant filename pattern**: `yolo11<scale>_<name>.yaml` — the `scale` in the filename must match one of the `SCALES` dict keys (`n`, `s`, `m`, `l`, `x`). `guess_model_scale()` from ultralytics overwrites the `scale` key in the YAML body with what it reads from the filename, so a file named `baseline_s.yaml` would silently build at scale `n`.

3. **Parameter count guards**: `BASELINE_PARAMS = {"n": 2_624_080, "s": 9_458_752}` — these are asserted in `tests/test_arch.py::test_baseline_matches_stock_yolo11_parameter_count` against the published YOLO11 counts.

4. **Module mode safety**: `tests/test_arch.py::test_module_mode_names_are_safe_for_parse_model` — mode names must be valid Python identifiers (not keywords like `global`), because `parse_model` uses `ast.literal_eval` to resolve them.

5. **Ledger consistency**: `ExperimentLedger` records every run; `python -m saryolo ledger` displays all records. The ledger is the source of truth for what was measured and what wasn't; `saryolo assets --require-complete` refuses to emit submission-ready tables while any cell is `TBD`.

6. **YAML regeneration**: `configs/models/` YAML files are generated from `VARIANTS` dict via `arch.py`. They should not be edited by hand; if a variant's behavior changes, the `VARIANTS` entry or the builder should be updated, not the YAML.

## Quick Configuration Reference

### To run the Streamlit demo:
```bash
# Default: uses weights/sarvo_ssac001.pt
streamlit run app.py

# With custom weights:
SARVO_WEIGHTS=/path/to/checkpoint.pt streamlit run app.py

# With custom input size:
streamlit run app.py  # then adjust imgsz in sidebar (320/512/640/800)
```

### To train on HRSID subset:
```bash
python -m saryolo train --exp configs/exp/REAL-001_hrsid_baseline.yaml
```

### To evaluate a checkpoint:
```bash
python -m saryolo eval --weights results/runs/REAL-004/weights/best.pt \
    --data configs/datasets/hrsid_real.yaml --imgsz 320
```

### To profile efficiency:
```bash
# Basic profiling
python -m saryolo efficiency --weights results/runs/REAL-004/weights/best.pt \
    --imgsz 320 --real --data configs/datasets/hrsid_real.yaml --batch 8 --runs 3

# SSAC sparse sweep at 320px (no saving expected at this scale)
python -m saryolo efficiency --weights results/runs/SSAC-001/weights/best.pt \
    --imgsz 320 --real --data configs/datasets/hrsid_real.yaml --batch 4 --runs 5 \
    --ssac-execution sparse --ssac-keep 1.0 --ssac-keep 0.5 --ssac-keep 0.25 --ssac-keep 0.1

# SSAC sparse sweep at 640px (saving appears at keep <= 0.5)
python -m saryolo efficiency --weights results/runs/SSAC-001/weights/best.pt \
    --imgsz 640 --real --data configs/datasets/hrsid_real.yaml --batch 4 --runs 5 \
    --ssac-execution sparse --ssac-keep 1.0 --ssac-keep 0.5 --ssac-keep 0.25 --ssac-keep 0.1 \
    --out results/efficiency/SSAC-001_640
```

### To generate paper tables:
```bash
python -m saryolo assets --require-complete  # fails if any cell is TBD
# or, to allow TBD cells:
python -m saryolo assets  # warns about incomplete cells
```

### To check data validity:
```bash
python -m saryolo check-data --dataset datasets/processed/hrsid_real.yaml --splits train val test
```
